# 설계 문서

1차 멘토링(10/11)에서 받은 피드백 네 가지에 대한 현재 답이다.

1. 모듈 단위 설계
2. 스트롱 베이스라인
3. 메트릭 수치화
4. 효율성 설계

## 1. 모듈 단위 설계

| 모듈 | 하는 일 | 지금 구현 | 다음 단계 |
|---|---|---|---|
| 구조화 (Structurer) | 자유 텍스트 기록을 topic·value·conditions·quote로 바꿈 | 데이터가 이미 구조화되어 있다고 가정. `llm.structure_record`는 작성만 됨 | 자유 텍스트 기록으로 구조화 정확도 측정 |
| 인용 검증 (Verifier) | 인용 구간이 원문 해당 버전에 실제로 있는지 판단 | 정확 일치 → 숫자 일치 확인 → 유사도. 애매 구간만 LLM | 바꿔 말한(paraphrase) 인용 케이스 추가, LLM 판정 정확도 측정 |
| PII 차단 (PII Guard) | 공유 사본에서 민감 정보 가리기 | 정규식(전화번호·이메일·주민번호·API 키). 인용 검증 뒤에 가림 | 실명 같은 형식 없는 정보는 `llm.detect_pii_spans`(작은 모델)로 연결. 지금은 예시 기록의 고객 실명이 가려지지 않음 |
| 관계 판정 (Relation Judge) | 새 기록과 기존 기록의 관계 판정 | topic·조건·근거 키 비교 규칙 | topic이 미묘하게 다른 경우는 임베딩 유사도와 작은 모델로 판정 |
| 저장소 (Store) | 후보/승인 상태, 관계 링크, 검토 요청 관리 | 메모리 | 승격 절차(누가 승인하나) 정의, 파일/DB 저장 |
| 리트리버 (Retriever) | 질문과 관련된 기록 찾기 | topic 일치 → BM25 | 임베딩 + BM25 하이브리드 |
| 답변 구성 (Composer) | 조건 필터, 상태 판정, 근거 중복 제거, 안내문 | 템플릿 | 같은 근거 묶음을 LLM에 넘겨 자연어 답변 생성 |

관계 판정 규칙은 발표 슬라이드의 표를 따른다. 여기에 `support`(같은 조건, 같은 주장, 다른 근거)를 추가했다.
`support`는 독립 근거 수를 셀 때 필요하다.

**조건 비교 규칙**: 질문과 기록에 모두 있는 조건 키의 값이 다르면 조건이 맞지 않는다.
기록에 없는 키는 제한 없음으로 본다. 예를 들어 결측치 기록은 피처 수와 무관하다.
이 규칙이 너무 관대한지는 팀이 논의해야 한다.

## 2. 베이스라인

| 구분 | 시스템 | 왜 | 상태 |
|---|---|---|---|
| **스트롱 (확정)** | **Graphiti** | 오픈소스. 출처 추적과 충돌 처리(시간 기반 무효화)가 있어 우리 문제와 가장 가깝다 | 어댑터 작성, 실행 검증 전 |
| 약한 | retrieval_only | 일반 RAG. 하네스가 없을 때의 기본 동작 | 동작 |
| 대조 | full_context_llm | "정보만 표로 넣어줘도 되지 않나?"에 답하기 위함. 큰 모델에 모든 정보를 준다 | 작성, API 키로 실행 필요 |
| 관련 연구 | SpeakerMem-R1 | 발언자/대상 분리와 이력 보존이 비슷함. 다만 RL 학습 기반이고 다인 대화 QA라서 재현 대신 관련 연구로 둔다 | - |

**Graphiti에 없는 페인 포인트** (우리 컨트리뷰션):

1. 조건이 다른 관찰을 충돌로 보고 하나를 무효 처리할 수 있다. 우리는 조건별로 나란히 보존한다. (1차 실행에서는 관찰되지 않음)
   - 대신 관찰된 것: **늦게 들어온 AI의 틀린 인용이 사람이 올린 올바른 사실을 무효화**했다 ([experiments.md](experiments.md))
2. 작성 주체(사람/AI)와 팀 승인 상태 구분이 없다.
3. 재인용을 독립 근거로 셀 수 있다.
4. 원문과 인용을 검증하는 계층이 없다.
5. 민감 정보(PII)가 팀 전체로 퍼지는 걸 막는 계층이 없다. (멘토 제안, 범위에 포함)

1~4는 **근거의 범위**, 5는 **공개 범위**가 공유되는 동안 넓어지는 문제다.
둘 다 "공유 범위 제어"라는 한 틀로 설명할 수 있다.

## 3. 메트릭

메인 메트릭은 **조건에 맞는 답변 비율(condition_match)** 하나로 좁힌다.
보조 메트릭은 각 모듈의 기여를 설명하는 데 쓴다.

| 메트릭 | 정의 | 어떤 모듈의 효과를 보나 |
|---|---|---|
| **condition_match** | 상태가 맞고, 조건 밖·인용 오류·무관한 근거를 쓰지 않은 답변 비율 | 전체 |
| overgeneralization | 같은 주제에서 질문 조건과 맞지 않는 기록을 근거로 쓴 비율 | 조건 비교 |
| irrelevant_used | 다른 주제의 기록을 근거로 쓴 비율(검색 품질) | 리트리버 |
| false_consensus | 승인 전 후보를 팀 사실로 제시한 비율 | 승인 상태 |
| bad_citation_used | 원문과 맞지 않는 인용을 근거로 쓴 비율 | 인용 검증 |
| evidence_error | 독립 근거 수 오차 | 재인용 묶기 |
| pii_leak | 답변·안내·넘겨준 근거 원문에 민감 정보가 그대로 남은 비율 | PII 차단 |

모든 시스템은 같은 `Response` 형식(상태, 근거 id, 팀 사실 id, 독립 근거 수)으로 답한다.
그래서 LLM 기반 시스템도 같은 기준으로 잴 수 있다.

발표 때 평가 3번 항목인 "추가 질문 없이 한 번에 원하는 답을 얻는가"는 사용자 실험이 필요하다.
이 항목은 이번 범위에서 빼거나 소규모 사용자 평가로 따로 하는 것을 제안한다.

### 평가 데이터 확장 (다음 단계)

현재 데이터는 기록 15개, 질문 14개짜리 합성 시나리오다. 하네스가 이 시나리오를 알고 만들어졌으므로 성능 비교 용도로는 부족하다.

- 실제 팀 실험 로그로 기록을 만든다. 우리 팀의 캡스톤 실험이나 공개 Kaggle 노트북 토론을 쓸 수 있다.
- 기록 작성과 질문/정답 작성을 다른 사람이 나눠 맡아 누출을 줄인다.
- 각 관계 유형(조건 다름, 재인용, 충돌, 인용 오류, 미승인)별로 최소 10건씩 확보한다.
- 기록을 자유 텍스트로 넣어 구조화 모듈 오류까지 포함한 end-to-end 성능을 잰다.

## 4. 효율성 설계

| 전략 | 내용 | 구현 |
|---|---|---|
| 모듈별 모델 크기 차등 | 구조화와 질문 파싱은 작은 모델(`claude-haiku-5-5`), 인용 검증 애매 구간은 큰 모델(`claude-opus-5-5`) | `harness/llm.py` |
| 규칙 우선, LLM은 애매할 때만 | 인용 검증은 정확 일치 → 숫자 확인 → 유사도 순으로 거르고, 애매 구간만 LLM에 넘김 | `verifier.py` |
| 인용 검증 캐시 | 근거 키(원문·버전·구간)가 같으면 다시 검증하지 않음. **재인용이 많을수록 히트가 남** (현재 데이터 13회 중 3회 히트) | `verifier.py` |
| 답변 캐시 | (topic, 조건, 저장소 버전) 키. 새 기록이 들어오면 버전이 바뀌어 자동 무효화 | `pipeline.py` |

측정할 것: 모듈별 호출 수, 토큰, 지연 시간을 기록해 "모든 단계를 큰 모델로" 대비 비용과 속도를 비교한다.
