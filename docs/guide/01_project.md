# 1편. 프로젝트 이야기

## 1. 한 문장으로

> **팀 기록이 AI들 사이에서 돌고 도는 동안 "원래 어디까지가 사실이었는지"를 잃지 않게 지켜주는 프로그램.**

프로젝트 이름 *Evidence-Bounded Knowledge Harness*를 풀면 이렇다.

- **Evidence-Bounded:** 근거의 범위 안에서만
- **Knowledge:** 지식을 다루는
- **Harness:** 마구(말에 채우는 장비) 또는 중간에서 연결하고 통제하는 장치

## 2. 비유로 이해하기: 조별과제 단톡방

5명이 조별과제를 한다고 해보자. 각자 AI 비서를 하나씩 쓰고, 알게 된 걸 단톡방에 올린다.

1. 민수가 실험해서 올린다. "**우리 반 데이터로 해보니** A 방법이 제일 좋았어."
2. 지은이의 AI가 그걸 요약해서 다시 올린다. "A 방법이 제일 좋다고 확인됨."
   **"우리 반 데이터로"라는 조건이 사라졌다.**
3. 다음 주에 **다른 반 데이터**로 과제를 하게 됐다. 누가 AI에게 묻는다. "어떤 방법 쓸까?"
   AI는 단톡방을 보고 "A 방법이 제일 좋습니다"라고 답한다. 하지만 다른 반 데이터에서 A가 좋은지는 **아무도 실험한 적이 없다.**
4. 같은 민수 결과를 세 명이 각자 다시 올렸다. AI는 "근거가 세 개나 있네"라고 생각한다. 실제 근거는 **하나**다.
5. 누군가의 AI가 "B 방법이 0.1점 더 좋았다고 기록돼 있다"고 올린다. 원래 기록에는 그런 말이 없다. **AI가 숫자를 잘못 옮겼다.**
6. 민수가 올린 글에 친구 전화번호가 섞여 있었다. 그 글을 AI들이 계속 인용하면서 **전화번호가 여기저기 퍼진다.**

이게 우리가 풀려는 문제다. 우리 하네스는 **단톡방과 AI 사이에 서 있는 꼼꼼한 총무**다.

- 글이 올라오면 "이거 어떤 조건에서 나온 결과야? 누가 썼어? 원문 어디야?"를 붙여 적어둔다.
- 원문을 직접 펼쳐서 인용이 맞는지 확인한다. 틀리면 근거에서 뺀다.
- 전화번호 같은 건 가린다.
- 같은 원문을 다시 인용한 글은 "같은 근거"로 묶어서 센다.
- 누가 물어보면 **질문 조건에 맞는 글만** 골라서 AI에게 준다. 그리고 이렇게 알려준다.
  - "이건 팀이 승인한 거야."
  - "이건 아직 한 사람 의견이야."
  - "이 조건으로는 아무도 실험 안 했어."
  - "두 사람 의견이 엇갈려."

## 3. 왜 시작했나 (계기)

- **관찰:** 요즘 실제 서비스들은 여러 AI 모델과 도구를 엮어서 하나의 "에이전트"로 돌리는 **하네스 구조**로 가고 있다. 1차 멘토링에서 멘토(삼성 AI팀 출신, 현재 네이버)도 이 흐름을 짚었다.
- **문제의식:** AI끼리 정보를 주고받는 일이 늘수록, 정보가 원래 가진 범위가 공유 과정에서 사라진다. 범위란 조건, 작성자, 근거, 팀 합의 여부다.
- **1차 멘토링 숙제 (10월 11일):**
  - 하네스가 어떤 **모듈**(부품)로 이뤄지는지 정할 것
  - 비교할 **강한 베이스라인**을 하나 잡을 것
  - **메트릭**(채점 기준)을 좁히고 숫자로 보여줄 것
  - **효율성**(속도·비용)도 고민할 것
  - 핵심 모듈이 실제로 도는 **데모**를 만들 것

이 저장소는 그 숙제의 결과물이다.

## 4. 목적: 무엇을 증명하려 하나

1. **정확성:** 하네스를 쓰면 AI가 조건 밖으로 일반화하거나, 개인 의견을 팀 사실로 말하는 일이 줄어드는가?
2. **효율성:** AI에게 필요한 기록만 넘겨서 읽을 양(비용)을 줄이는가?
3. **안전성:** 민감 정보가 AI나 다른 팀원에게 새어나가지 않는가?
4. **베이스라인 대비 기여:** 이미 있는 도구(Graphiti)에는 없는 무엇을 우리가 하는가?

## 5. 용어 사전

처음 나오는 어려운 말은 여기서 찾으면 된다.

| 용어 | 쉬운 뜻 |
|---|---|
| **AI / LLM** | 글을 읽고 쓰는 인공지능. ChatGPT, Claude 같은 것. LLM은 "거대 언어 모델"의 줄임말 |
| **에이전트** | 스스로 도구를 쓰면서 일을 처리하는 AI 프로그램 |
| **하네스** | 여러 AI와 도구 사이에서 정보를 정리하고 통제하는 중간 프로그램. 우리 프로젝트에서는 "꼼꼼한 총무" |
| **모듈** | 프로그램을 이루는 부품 하나. 인용 검증 모듈, PII 차단 모듈 등 |
| **기록 (record)** | 팀원이나 AI가 팀에 공유한 글 한 개. 우리 데이터에서는 R01~R15 |
| **원문 (source)** | 기록이 근거로 삼은 실험 보고서. exp_001 같은 문서 |
| **인용 (quote)** | 기록이 원문에서 따왔다고 주장하는 문장 |
| **조건 (conditions)** | 결과가 성립하는 상황. 예: 피처 12개, 데이터 v1 |
| **피처 (feature)** | 머신러닝 모델에 넣는 입력 항목. 예: 가입기간, 월 요금. "피처 12개" = 입력 항목 12개 |
| **데이터 버전 (v1, v2)** | 데이터를 언제, 어떻게 모았는지에 따른 판. v2는 10월에 추가로 모은 데이터 |
| **승인 (approved) / 후보 (candidate)** | 팀이 합의해서 인정한 기록 / 아직 한 사람(또는 AI)의 의견인 기록 |
| **재인용** | 이미 누가 인용한 원문 구간을 다른 사람이 다시 인용한 것. 근거가 늘어난 게 아니다 |
| **충돌 (conflict)** | 같은 조건에서 서로 다른 결론이 있는 것 |
| **PII** | Personally Identifiable Information. 이름, 전화번호, 이메일처럼 사람을 알아낼 수 있는 정보. 우리는 API 키 같은 비밀 정보도 같이 다룬다 |
| **정규식 (regex)** | "숫자 3개-4개-4개" 같은 글자 패턴을 찾는 규칙. 전화번호 찾기에 쓴다 |
| **베이스라인** | 비교 기준이 되는 기존 방식. "이것보다 나아졌다"를 보여주려면 필요하다 |
| **스트롱 베이스라인** | 약한 상대가 아니라 현재 잘한다고 알려진 강한 상대. 우리는 Graphiti |
| **Graphiti** | 대화와 문서를 지식 그래프로 정리하는 오픈소스 도구. 출처 추적과 "옛 정보 무효 처리" 기능이 있다 |
| **지식 그래프** | 정보를 점(사람·사물)과 선(관계)으로 연결해 저장하는 방식 |
| **Neo4j** | Graphiti가 그래프를 저장하는 데이터베이스 프로그램 |
| **BM25** | 검색 엔진에서 오래 쓴 "단어가 얼마나 겹치나" 점수 계산법 |
| **RAG** | 질문과 비슷한 글을 검색해서 AI에게 같이 주고 답하게 하는 방식 |
| **맥락 (context)** | AI에게 질문과 함께 넘겨주는 참고 자료. 길수록 AI가 읽을 게 많아 비싸고 느려진다 |
| **메트릭** | 채점 기준. 예: 조건 일치 답변률 |
| **캐시** | 한 번 계산한 결과를 저장해두고 다시 쓰는 것. 같은 질문에 다시 돈을 쓰지 않게 해준다 |
| **ablation (모듈 끄기 실험)** | 부품을 하나씩 빼보고 어떤 점수가 나빠지는지 보는 실험. 각 부품의 기여를 보여준다 |
| **합성 데이터** | 실제가 아니라 실험용으로 직접 만든 데이터 |
| **JSON** | `{"이름": "값"}` 모양으로 데이터를 적는 파일 형식 |
| **클래스 / 함수** | 코드에서 "설계도"(클래스)와 "동작 하나"(함수) |
| **API 키** | 유료 AI 서비스를 쓸 때 필요한 비밀번호 같은 문자열 |

## 6. 큰 그림: 하네스 안에서 일어나는 일

### 기록이 들어올 때 (총무가 글을 받을 때)

```
새 기록 (예: "XGBoost가 제일 좋다", 근거: exp_001 "XGBoost AUC 0.842")
   │
   ├─① 인용 검증: exp_001을 펼쳐서 "XGBoost AUC 0.842"가 진짜 있는지 확인
   ├─② PII 차단: 전화번호·이메일·키·실명이 있으면 [가림]으로 바꿈
   ├─③ 구조화: 이 글의 주제(best_model), 값(XGBoost), 조건(피처 12개, v1)을 뽑음
   ├─④ 관계 판정: 기존 기록과 비교 → 새 글 / 조건 다름 / 재인용 / 지지 / 충돌
   └─⑤ 저장: 충돌이면 양쪽 모두에 "검토 필요" 표시
```

### 질문이 들어올 때 (누가 총무에게 물어볼 때)

```
질문 (예: "피처 40개, 데이터 v1에서 어떤 모델 쓸까?")
   │
   ├─① 질문 파싱: 주제 = best_model, 조건 = 피처 40개, v1
   ├─② 검색: 주제가 같은 기록을 모두 찾음
   ├─③ 조건 필터: 피처 12개짜리 기록은 "조건 다름"으로 빼냄
   ├─④ 인용 오류 기록 제외
   ├─⑤ 상태 판정: 답할 수 있음 / 충돌 / 승인 전 후보뿐 / 근거 없음
   └─⑥ AI 답변기에 "판정 + 조건 맞는 기록 + 안내"를 넘김
         → AI: "피처 40개 조건에 맞는 팀 근거가 없습니다. 기존 결과는 피처 12개 조건입니다."
```

## 7. 폴더 지도

```
knowledge_harness/
├── harness/     ← 우리가 만든 시스템 (총무 본체)            → 3편
├── baselines/   ← 비교 대상 3가지                           → 4편
├── eval/        ← 실험을 돌리고 채점하는 곳                 → 4편
├── data/        ← 실험용 가짜 팀 기록·원문·질문             → 2편
├── scripts/     ← 보조 도구 (Graphiti 연결 확인, 그래프)    → 4편
├── tests/       ← 코드가 망가지지 않았는지 자동 확인        → 4편
├── docs/        ← 문서 (설계, 실험 기록, 이 설명서)
├── requirements.txt  ← 설치할 외부 패키지 목록
└── .gitignore        ← git에 올리지 않을 파일 목록 (캐시, 결과, 가상환경)
```

### 폴더끼리 어떻게 일하나: 시험 보는 장면으로 비유

| 실제 | 비유 |
|---|---|
| `data/` | 시험 문제지와 정답지, 그리고 참고서(팀 기록) |
| `harness/`, `baselines/` | 시험을 보는 학생들. 하네스 1명 + 비교 대상 3명 |
| `eval/run_eval.py` | 시험 감독관. 학생들에게 참고서를 나눠주고 문제를 하나씩 낸다 |
| `eval/metrics.py` | 채점 기준표. 답안을 정답과 비교해서 점수를 매긴다 |
| `results/` | 채점 결과지 (실행하면 생긴다) |

실행 순서는 이렇다.
1. 감독관(`run_eval.py`)이 참고서(`records.json`)와 문제지(`queries.json`)를 읽는다.
2. 학생(시스템)을 한 명씩 불러 참고서를 모두 읽게 한다. 코드에서는 `ingest`라고 부른다.
3. 문제를 하나씩 내고 답안을 받는다. 코드에서는 `ask`라고 부른다.
4. 채점 기준표(`metrics.py`)로 채점한다.
5. 점수표를 화면에 찍고 `results/`에 저장한다.

모든 학생은 **같은 모양의 답안지**(`Response`)를 낸다. 그래서 같은 기준으로 공정하게 채점할 수 있다.

## 8. 2차 멘토링까지 한 일 (시간 순서)

| 순서 | 한 일 | 왜 |
|---|---|---|
| 1 | 모듈 설계, 합성 데이터 만들기, rule 모드 데모 | 멘토 숙제: 모듈 구성과 데모 |
| 2 | 스트롱 베이스라인을 Graphiti로 확정 | 멘토 숙제: 베이스라인 |
| 3 | PII 차단 모듈 추가 | 멘토 제안: 현업에서 가장 뜨거운 주제가 정보 유출 |
| 4 | Graphiti 실제 실행 (1차 실험) | 비교해보니 공정하지 않은 점이 보였다 |
| 5 | 공정 비교 방식으로 다시 설계 (2차 실험) | 모든 시스템에 같은 재료, 같은 AI 답변기 |
| 6 | 애매한 정답 3개 수정, PII 지표 분리 | 정답 라벨이 애매했던 걸 발견 |
| 7 | 규모 실험 (기록 15 / 115 / 315개, 3차 실험) | 기록이 많아지면 어떻게 되나 |
| 8 | 하네스 안내문이 늘어나는 문제 수정 | 맥락 크기가 일정해지도록 |
| 9 | 그래프, 발표 흐름 정리 | 2차 멘토링 준비 |
