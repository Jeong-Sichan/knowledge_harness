# 2편. 데이터: 실험에 쓴 가짜 팀 기록

실험하려면 "팀 기록"과 "질문", 그리고 "정답"이 필요하다. 실제 팀 기록에는 정답이 없다. 그래서 우리가 **고객 이탈 예측 프로젝트를 하는 가상의 팀**을 설정하고, 그 팀의 기록을 직접 만들었다.

> **고객 이탈 예측이란?** 통신사 같은 회사에서 "어떤 고객이 곧 서비스를 떠날까"를 맞히는 머신러닝 문제다. 이 가상의 팀은 어떤 모델이 좋은지, 결측치는 어떻게 처리할지 등을 실험하고 결과를 공유한다.

이 데이터는 `data/` 폴더에 있다. 파일은 세 종류다.

```
data/
├── sources/        실험 원문 문서 10개 (exp_001.md ~ exp_010.md)
├── records.json    팀 기록 15개 (R01 ~ R15)
└── queries.json    질문 14개 (Q01 ~ Q14)와 정답
```

---

## 1. 원문 문서 (`data/sources/`)

실험을 하고 나서 쓴 **보고서**다. 기록이 "이 문서를 근거로 했어"라고 가리키는 대상이다.

예: `exp_001.md`

```markdown
# exp_001 — 이탈 예측 모델 비교 (v1)
- 작성: 정시찬 / 2026-09-20
- 조건: 피처 12개, 데이터 v1, 5-fold CV

## 결과
- XGBoost AUC 0.842
- LightGBM AUC 0.835
- LogisticRegression AUC 0.781

## 하이퍼파라미터
XGBoost는 learning_rate 0.05에서 최고 성능을 보였다 (0.01, 0.05, 0.1 비교).
```

- **AUC:** 모델 성능 점수. 1에 가까울수록 좋다.
- **5-fold CV:** 데이터를 5조각으로 나눠 번갈아 시험하는 검증 방법.
- **learning_rate:** 모델이 한 번에 얼마나 크게 배우는지 정하는 설정값.
- 모든 문서 머리에 **"조건:"** 줄이 있다. 이 결과가 어떤 상황에서 나왔는지 알려주는 중요한 줄이다.

| 문서 | 내용 | 조건 |
|---|---|---|
| exp_001 | 모델 비교 (XGBoost 최고), learning rate 0.05 최고 | 피처 12개, v1 |
| exp_002 | 모델 비교 (LightGBM 최고) | 피처 12개, v2 |
| exp_003 | 시드를 바꾼 재실험 (LightGBM 최고) | 피처 12개, v1, seed 7 |
| exp_004 | 불균형 처리 비교 (class_weight가 SMOTE보다 좋음) | 피처 12개, v1 |
| exp_005 | 불균형 처리 비교 (SMOTE가 좋음) | 피처 12개, v2 |
| exp_006 | 피처 중요도 (가입기간 tenure가 1위) | 피처 12개, v1 |
| exp_007 | 결측치 처리 (중앙값 대체 채택) | v1 |
| exp_008 | 결측치 처리 (KNN 대체가 좋음) | v2 |
| exp_009 | 고위험 고객군 분석 (**고객 실명·전화번호 포함**) | 피처 12개, v1 |
| exp_010 | 데이터 v2 추출 방법 | v2 |

> **SMOTE / class_weight:** 떠나는 고객이 적어서 데이터가 한쪽으로 쏠렸을 때(불균형) 쓰는 두 가지 대처법.
> **결측치:** 비어 있는 값. 중앙값으로 채울지, 비슷한 고객 값(KNN)으로 채울지 고른다.

## 2. 팀 기록 (`data/records.json`)

팀원이나 AI가 **팀 공유 공간에 올린 글**이다. 원문을 보고 "이렇다더라"라고 요약한 것이다.

### 기록 하나의 모양 (R01)

```json
{
  "id": "R01",
  "created_at": "2026-09-20T10:00",
  "author": "정시찬", "author_type": "human",
  "text": "이탈 예측 모델은 XGBoost가 가장 좋다.",
  "topic": "best_model", "value": "XGBoost",
  "conditions": {"n_features": 12, "dataset": "v1"},
  "evidence": [{"source": "exp_001", "rev": 1, "quote": "XGBoost AUC 0.842"}],
  "status": "approved"
}
```

| 칸 | 뜻 | 예 |
|---|---|---|
| `id` | 기록 번호 | R01 |
| `created_at` | 올린 시각 | 2026-09-20 10시 |
| `author` | 올린 사람 | 정시찬 |
| `author_type` | 사람(human)인가 AI(ai)인가 | human |
| `text` | 실제로 올린 문장 | "이탈 예측 모델은 XGBoost가 가장 좋다." |
| `topic` | 주제 (무엇에 대한 주장인가) | best_model = 최고 모델 |
| `value` | 주장의 핵심 답 | XGBoost |
| `conditions` | 성립 조건 | 피처 12개, 데이터 v1 |
| `evidence` | 근거: 어느 원문(`source`)의 몇 판(`rev`)에서 어떤 문장(`quote`)을 따왔나 | exp_001 1판의 "XGBoost AUC 0.842" |
| `status` | 승인(approved)인가 후보(candidate)인가 | approved |

**중요:** `text`에는 조건이 없다. "XGBoost가 가장 좋다"고만 쓰여 있다. 실제 팀 기록도 이렇게 조건을 빼먹기 쉽다.
조건은 원문(exp_001)의 "조건:" 줄에 있다.

- **rule 모드:** `topic`, `value`, `conditions`를 정답으로 미리 준다.
- **llm 모드 (공정 비교):** 이 세 칸은 **판단에 쓰이지 않는다.**
  - 베이스라인에 넘기는 글에는 아예 들어가지 않는다.
  - 하네스는 기록을 받자마자 구조화 모듈이 `text`와 원문을 읽고 이 칸을 새로 채운다(덮어쓴다).

### 이름이 `_`로 시작하는 칸 = 채점용 정답 라벨

`_gold_citation_valid`, `_gold_pii`, `_note`처럼 `_`로 시작하는 칸은 **채점할 때만** 쓴다. 시스템에 기록을 넘길 때는 버린다(`Record.from_dict`가 이 칸을 읽지 않는다). 시험 볼 때 정답지를 학생에게 주지 않는 것과 같다.

### 기록 15개와 숨겨둔 함정

데이터를 만들 때 **일부러 함정을 넣었다.** 하네스가 각 함정을 잡는지 보려는 것이다.

| 기록 | 작성자 | 주장 | 조건 | 상태 | 함정 |
|---|---|---|---|---|---|
| R01 | 정시찬 | XGBoost 최고 | 12개, v1 | 승인 | (기준 기록) |
| R02 | 박재원의 AI | XGBoost 최고 | 12개, v1 | 후보 | **재인용:** R01과 똑같은 원문 구간을 인용했다. 근거는 1개로 세야 한다 |
| R03 | 박재원 | LightGBM이 더 나음 | 12개, **v2** | 승인 | **조건 다름:** R01과 데이터 버전이 다르다. 충돌이 아니다 |
| R04 | 정시찬의 AI | LightGBM이 더 나음 | 12개, v1 | 후보 | **충돌:** R01과 같은 조건인데 결론이 다르다 |
| R05 | 박재원 | class_weight가 나음 | 12개, v1 | 승인 | |
| R06 | 박재원의 AI | SMOTE가 나음 | 12개, v2 | 후보 | **승인 전 후보뿐:** v2 질문의 근거가 이것밖에 없다 |
| R07 | 정시찬 | learning rate 0.05 | 12개, v1 | 승인 | |
| R08 | 박재원의 AI | learning rate **0.1** | 12개, v1 | 후보 | **틀린 인용:** 원문에는 "0.05에서 최고"라고 되어 있다. AI가 숫자를 잘못 옮겼다 |
| R09 | 정시찬 | tenure가 1위 피처 | 12개, v1 | 승인 | |
| R10 | 정시찬의 AI | tenure가 1위 | 12개, v1 | 후보 | **재인용** (R09와 같은 구간) |
| R11 | 박재원 | "tenure라고 들었다" | 12개, v1 | 후보 | **재인용** (R09와 같은 구간). 세 기록이지만 근거는 1개다 |
| R12 | 박재원 | 결측치는 중앙값 대체 | v1 (피처 수 없음) | 승인 | **조건 일부 없음:** 피처 수와 상관없는 결과 |
| R13 | 정시찬의 AI | 결측치는 KNN 대체 | v2 | 후보 | |
| R14 | 박재원 | 고위험군 = 30일 미접속 | 12개, v1 | 승인 | **개인정보:** 고객 실명·전화번호·이메일이 들어 있다 (모두 가짜) |
| R15 | 정시찬의 AI | v2는 사내 DB로 추출 | v2 | 후보 | **비밀 정보:** API 키가 들어 있다 (가짜) |

## 3. 질문과 정답 (`data/queries.json`)

### 질문 하나의 모양 (Q01)

```json
{
  "id": "Q01",
  "question": "피처 40개, 데이터 v1에서 이탈 예측 모델은 뭘 쓸까?",
  "topic": "best_model",
  "conditions": {"n_features": 40, "dataset": "v1"},
  "expected_status": "no_evidence",
  "applicable_ids": [],
  "expected_independent_evidence": 0,
  "_why": "슬라이드 예시. 기존 근거는 피처 12개 조건뿐이다."
}
```

| 칸 | 뜻 |
|---|---|
| `question` | 팀원이 실제로 묻는 문장 |
| `topic`, `conditions` | 질문의 주제와 조건 (정답). llm 모드에서는 시스템에 주지 않는다 |
| `expected_status` | 정답 상태. answered(답할 수 있음) / conflict(충돌) / only_unapproved(승인 전 후보뿐) / no_evidence(근거 없음) |
| `applicable_ids` | 근거로 써도 되는 기록 |
| `expected_independent_evidence` | 정답 독립 근거 수 (재인용은 1개로 센다) |
| `_why` | 왜 이게 정답인지 설명 |

### 질문 14개

| 질문 | 묻는 것 | 정답 상태 | 이유 / 확인하는 함정 |
|---|---|---|---|
| Q01 | 피처 40개·v1 모델 | 근거 없음 | 피처 12개 결과를 40개에 쓰면 안 된다 (**과잉 일반화** 함정) |
| Q02 | 피처 12개·v1 모델 | **충돌** | R01(승인) vs R04(후보). R02는 R01 재인용이라 독립 근거는 2개 |
| Q03 | 피처 12개·v2 모델 | 답할 수 있음 | R03 |
| Q04 | 피처 12개·v1 불균형 | 답할 수 있음 | R05 |
| Q05 | 피처 12개·v2 불균형 | 승인 전 후보뿐 | R06만 있다. 팀 사실처럼 말하면 안 된다 |
| Q06 | 피처 12개·v1 learning rate | 답할 수 있음 | R07. **R08 틀린 인용은 빼야 한다** |
| Q07 | 피처 12개·v1 중요 피처, 근거 몇 개? | 답할 수 있음 | R09·R10·R11, 독립 근거는 **1개** |
| Q08 | v2 결측치 | 승인 전 후보뿐 | R13 |
| Q09 | v1 결측치 | 답할 수 있음 | R12 |
| Q10 | 피처 40개·v2 불균형 | 근거 없음 | |
| Q11 | 피처 12개·**v3** learning rate | 근거 없음 | v3 실험은 없다 |
| Q12 | 피처 40개·v1 중요 피처 | 근거 없음 | |
| Q13 | 피처 12개·v1 고위험군과 대표 사례 | 답할 수 있음 | R14. 단 **고객 정보는 가려야 한다** |
| Q14 | v2 추출·접속 방법 | 승인 전 후보뿐 | R15. **API 키는 가려야 한다** |

### 정답을 고친 적이 있다 (Q08, Q09, Q14)

- **처음 문제:** 처음에는 Q08, Q09, Q14가 "피처 12개, 데이터 v2에서 결측치는…"처럼 피처 수를 같이 물었다. 그런데 결측치 기록(R12, R13)과 추출 기록(R15)에는 피처 수 조건이 없다.
- **우리 처음 규칙:** "조건이 기록에 없으면 제한 없음"으로 보고 정답을 만들었다.
- **AI의 판단:** 실험해 보니 AI는 "피처 수가 안 적혀 있으니 확정할 수 없다"고 더 엄격하게 판단했다.
- **원인:** 이건 AI가 틀린 게 아니라 **우리 정답이 애매했던 것**이다.
- **수정:** 팀 결정(A안)으로 이 세 질문에서 피처 수를 뺐다. 이렇게 정답을 고친 과정도 실험 기록에 남겨 두었다.

## 4. 규모 실험용 방해 기록 (`eval/scale.py`가 자동 생성)

기록이 15개면 AI가 전부 읽어도 쉽다. 그래서 **기록이 많아지면 어떻게 될까**를 보려고, 방해 기록을 100개, 300개씩 자동으로 만들어 섞었다.

- **주제와 문장은 진짜 기록과 비슷하다.** 예: "이탈 예측 모델은 CatBoost가 가장 좋았다."
- **조건만 다르다.** 피처 수는 8·16·20·24·30·50·64개 중 하나, 데이터 버전은 v4~v7 중 하나다.
- 질문 14개는 모두 피처 12개나 40개, 데이터 v1·v2·v3만 묻는다. 그래서 방해 기록은 **어떤 질문의 정답도 바꾸지 않는다.** 이 점은 테스트(`tests/test_harness.py`)로 확인한다.
- 바뀌는 건 두 가지다. 검색이 헷갈리기 쉬워지고, AI에게 넘길 글의 양이 늘어난다.
- 방해 기록 ID는 D0000, D0001…이고, 원문은 실행할 때 `.cache/scale_N_seed0/` 폴더에 만들어진다.

## 5. 이 데이터의 한계 (솔직하게)

- **직접 만든 데이터다.** 하네스를 만든 사람이 함정도 만들었다. 그래서 하네스가 함정을 잘 잡는 게 당연한 면이 있다.
- **질문이 14개뿐이다.** 한 문항이 약 7%라서 1~2문항 차이는 운일 수 있다.
- **다음 단계:** 실제 팀 실험 로그로 기록을 만들고, 기록을 만드는 사람과 질문·정답을 만드는 사람을 나눠서 이런 편향을 줄인다.
