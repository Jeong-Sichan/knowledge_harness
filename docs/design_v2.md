이 문서는 기존 하네스(`harness/`)와 팀원 레포([ashcircle03/evidence-bounded-team-memory](https://github.com/ashcircle03/evidence-bounded-team-memory))의 문제를 함께 고려해서, **MCP 서버 형태의 새 하네스(v2)** 를 밑바닥부터 다시 설계한 기록이다.
결정은 D1부터 D15까지 순서대로 정했고, 각 결정은 앞 결정에 기대어 있다. 새 작업 세션은 이 문서 전체를 먼저 읽고 시작한다.

## 1. 배경

### 1.1 프로젝트
- 데이터 분석 캡스톤, 팀 YUSINESS (박재원, 정시찬).
- 이름: Evidence-Bounded Knowledge Harness.
- 한 문장 정의(D1): **팀원의 AI가 팀 기록을 쓰고 읽을 때, 근거가 허용하는 범위 안에서만 쓰고 답하게 만드는 검문소.**

### 1.2 기존 하네스 (v1, `harness/`)
- 입력 길: 인용 검증 → PII 가림 → (LLM 구조화) → 관계 판정 → 저장
- 질문 길: (질문 파싱) → 검색(주제 → BM25) → 답변 구성(조건 필터, 인용 오류 제외, 승인 구분, 재인용 묶기, 상태 4가지)
- 답변 상태 4가지: answered(답할 수 있음) / conflict(충돌) / only_unapproved(승인 전) / no_evidence(근거 없음)
- 주요 결과
  - 자체 데이터 LLM 모드 14문항: 기록 15·115·315개에서 하네스 조건 일치 1.00, 전체 맥락 LLM 1.00/0.86/0.93, Graphiti 0.36. 하네스 맥락 약 330자 대 전체 맥락 약 87,000자(315개). PII 노출 0.
  - GroupMemBench 100문항(Finance 60 + Technology 40): 하네스 0.71(95% CI 0.62–0.80) 대 bm25 0.59, McNemar p=0.036. 이득은 대부분 abstention(0.88 대 0.67)에서 났고, knowledge_update는 0.55 대 0.51. 근거 판정을 끄면 0.62로 bm25 수준, 범위 지정은 효과 없음. Graphiti 0.47(KU 0.14), 입력 138분.

### 1.3 팀원 레포 요약
- Git으로 기록을 공유하는 팀 기억 시스템. 기록 = 불변 JSON 파일(파일 이름 = 내용 해시).
- 기록 필드: owner, issue, value, scope(조건), quote(원문에 글자 그대로 있어야 함), source(원문 전체 포함), reason_quote, corrects.
- 관계: 문장 틀(주장·조건 값을 빈칸으로 바꾼 문장)이 같을 때만 비교 → duplicate / keep_by_condition / propose_correction / unresolved / needs_comparison.
- 승인: 관계가 생긴 기록의 주인 모두가 투표해야 확정. 정정(corrects) 승인 시 옛 기록은 superseded.
- 재검토 제안(`reconsider.py`): 결정 단어 정규식으로 과거 결정을 찾고, Qwen2.5-3B에게 새 기록 없이/있이 두 번 A~E를 고르게 함.
- QA: 원문과 기록을 BM25로 찾고, Qwen이 메시지·문장 번호로 답 위치를 고르면 코드가 글자 그대로인지 검사.
- 실험: CPython PEP 3건(목표 5개, QA 9회), 정답·기준을 해시로 사전 고정, 호출 기록 재생. 결과: 대상+조치 결합 정답 단순 2/5, 모듈 1/5, 단순 재확인 2/5. QA 0/9(검색은 9번 모두 성공, 답 고르기에서 실패). 모듈 채택 보류.

## 4. 결정 상세

### D1. 목적과 범위 — 확정

**한 문장 정의:** 팀원의 AI가 팀 기록을 쓰고 읽을 때, 근거가 허용하는 범위 안에서만 쓰고 답하게 만드는 검문소.

**사용자:** 데이터 분석·ML 실험을 하는 2~6명 팀. 팀원마다 자기 AI(Claude, ChatGPT 등)를 씀.

**막을 실패 (= 성공 기준)**
| # | 실패 | 예 | 지표 |
|---|---|---|---|
| 1 | 조건을 넘는 일반화 | 피처 12개 결과를 40개 질문의 답으로 씀 | 조건 일치율, 과잉 일반화율 |
| 2 | 미승인 후보를 팀 사실처럼 말함 | 작성자가 확인 안 한 AI 추출 결과를 사실로 답함 (D7 이후 의미) | 상태 정확도 |
| 3 | 재인용을 독립 근거로 셈 | 같은 실험 하나를 근거 3개처럼 말함 | 거짓 합의율 |
| 4 | 틀린 인용을 근거로 씀 | 원문은 0.05인데 0.1로 인용 | 잘못된 인용 사용률 |
| 5 | 바뀐 결정을 모르고 옛 결정으로 답함 (신규) | 정정·대체된 결정을 현재 결정으로 답함 | 옛 결정 답변율 |
| ~~6~~ | ~~민감 정보 확산~~ | D11에서 향후 과제로 이동. 1차 범위는 정규식 최소 조치만, 지표 제외 | — |

**하지 않는 것**
| 안 하는 것 | 이유 |
|---|---|
| 결정을 대신 내리기 | 근거와 상태만 제시 |
| 최종 답 문장 생성 | 팀원의 AI가 씀. 하네스는 근거·상태·규칙을 주고 검사만 (D9) |
| 자동 승인 | 승인은 사람만 (D7) |
| 일반 문서 검색(RAG) 대체 | 팀의 결정과 실험 결과 기록에 한정 |

**채팅 범위: (a) 확정.** 1차 범위는 실험 결과·결정을 담은 팀 기록. 채팅·회의록은 원문으로 저장하고 인용할 수는 있지만, 채팅에서 결정을 자동 추출하는 것은 2차 범위.
- 기각한 (b): 채팅 자동 추출까지 1차에 넣기. 질문당 LLM 판정 필요(H7), 단어 규칙 실패 전례(T2)로 난이도 큼.

### D2. 기본 단위: 데이터 모델 — 확정

**다룬 문제:** H1(주제 이름 의존), T6(원문 진위·버전 검사 불가)

**① 저장하는 객체는 4종(+향후 1종), 나머지는 계산**
```
[원문 Source] ◀── 인용 ── [주장 Claim] ◀── 투표 ── [투표 Vote]
                              ▲
                           [별칭 Alias] (선택, 주제·조건 키 중복 합치기)
(향후: [원문 숨김 Hide], D11)

계산(저장 안 함): 인용이 맞는지, 주장 사이의 관계, 현재 상태, 주제·조건 키 목록, 주제별 관련 조건 키
```
- 상태·관계를 저장하면 규칙이 바뀔 때 옛 판정과 섞이므로, 매번 계산한다(팀원 레포 `replay` 방식). 느리면 캐시.

**② 주장은 원문을 id + 버전으로 참조, 본문을 품지 않음** (T6 해결)

**③ 주장 하나 = 한 조건에서 한 가지 주장.** 원문 하나에서 주장 여러 개가 나올 수 있음.

**④ 주장 종류: 관측(observation) / 결정(decision)**
| 종류 | 뜻 | 예 |
|---|---|---|
| 관측 | 어떤 조건에서 측정·관찰한 결과 | "v1에서 XGBoost AUC 0.842, 가장 좋다" |
| 결정 | 팀이 채택·기각·보류한 것 | "결측치는 중앙값 대체를 채택했다" |
- 이유: 관측끼리 다르면 둘 다 사실일 수 있음(비교 필요), 결정끼리 다르면 하나가 다른 하나를 대체했는지가 핵심. 막을 실패 5번은 결정에서만 생김.

**⑤ 주장은 고치지 않음. 정정은 `corrects`를 단 새 주장.** 옛 주장은 "정정됨/대체됨"으로 계산되고 이력은 남음.

**⑥ 작성 책임자와 작성 주체 분리**
| 칸 | 뜻 |
|---|---|
| `author` | 책임지는 팀원 (글을 올린 사람) |
| `written_by` | 실제로 쓴 주체. `{"type":"ai","model":"…","client":"…"}` 또는 `{"type":"human"}` |
- 결정권자 요청으로 AI는 모델명을 기록. D4 확정 후에는 주장을 서버 LLM이 뽑으므로 `written_by`에는 **서버 LLM 모델명 + 지시문 버전**이 들어간다(자기 신고가 아니라 서버가 아는 값).

**⑦ 주제·조건 키 목록은 자동으로 쌓임 (수동 등록 없음)**
- 저장된 주장에 쓰인 주제·조건 키를 모은 것이 목록(계산).
- 결정권자 결정: **팀원의 AI에게 올리기 전 목록을 보여주는 단계는 없음.**
- 같은 주제 판단은 D4에서 서버 LLM이 서버 안에서 목록을 보고 함(사용자 쪽에 보여주는 것이 아니므로 위 결정과 충돌 없음).
- 그래도 생긴 중복은 사람이 별칭 기록으로 합침(선택).

**id 규칙:** 모든 저장 객체의 id = 내용 해시. 내용이 바뀌면 id도 바뀌어 몰래 고칠 수 없음.

**충돌 시 상대 작성자 승인 원칙:** 결정권자 요청. D6·D7에서 구체화.

**예시 (R12를 새 형식으로)**
```json
// 원문
{"id": "src_a91c…", "doc": "exp_007", "rev": 1, "kind": "experiment_log",
 "author": "박재원", "created_at": "2025-…", "location": "experiments/exp_007.md",
 "text": "…결측치 처리 방법을 비교한 결과 중앙값 대체를 채택했다…"}

// 주장
{"id": "clm_5e02…", "kind": "decision",
 "topic": "missing_value", "value": "median", "conditions": {"dataset": "v1"},
 "statement": "결측치는 중앙값 대체로 처리한다.",
 "evidence": [{"source": "src_a91c…", "quote": "중앙값 대체를 채택했다", "start": 120, "end": 132}],
 "reason": null, "author": "박재원",
```

### D3. 원문 저장과 인용 검증 — 확정 (C안)

**다룬 문제:** T6, 기존 하네스의 느슨한 유사도 기준

**"인용이 필요한가?"에 대한 논의 결과:** 필요함. 인용은 근거 확인, 재인용 구분, 새 버전 확인, 작은 맥락, 사람 검토를 가능하게 함. 단, 인용이 보장하는 것은 **"이 문장이 그 버전 원문에 있다"까지**이고 "이 문장이 주장을 뒷받침한다"는 아님 → 의미 확인은 사람 승인(D7).
- 기각한 B안: 문서만 참조(인용 없음).

**① 원문은 본문 텍스트를 통째로 저장.** 이름은 `문서 이름@버전`. 같은 문서 이름에 다른 내용이 오면 자동으로 다음 버전. 위치(경로·URL)는 참고 정보.

**② 인용은 원문에 글자 그대로 있어야 함 (공백·줄바꿈 차이만 허용).**
- 기존 하네스의 "유사도 0.92 이상 통과"를 버림. 이유: 부정문을 못 잡음("개선되지 않았다" → "개선되었다"가 통과).
- 거부 시 원문에서 가장 비슷한 구간을 같이 알려줌.
- 인용 위치(start/end)는 서버가 찾아 붙임.

**③ (C안) 300자 이하 짧은 원문은 원문 전체를 인용으로 자동 처리.**

**④ 틀린 인용은 저장하지 않고 입구에서 거부.** (기존 하네스는 저장 후 질문 때 제외했음) 기존 노트를 한꺼번에 들여올 때는 실패 목록을 돌려줌.

**⑤ 원문에 새 버전이 생겨도 옛 주장은 유효(당시 근거).** 질문 답할 때 서버가 인용 문장이 최신 판에도 있는지 확인해 "최신 원문에서도 확인됨" / "최신 원문에서 사라짐, 재확인 필요"를 붙임.

**⑥ 원문도 불변.** 문제 원문 처리는 D11(향후 과제).

**⑦ 이 단계에서 LLM은 쓰지 않음.**

### D4. 구조화 — 확정 (수정안)

**다룬 문제:** H1, T3, D2에서 남긴 주제 중복 문제

**결정권자 의견으로 바뀐 점:** 처음 제안은 "팀원의 AI가 구조화하고 서버는 규칙 검사만"이었으나, 결정권자가 다음을 지적해 수정함.
- 매번 입력 형식·작성 규칙을 맞추게 하지 말고 자유롭게 써야 함 → **서버 LLM이 구조화.**
- 서버가 모든 걸 규칙으로 처리하면 예외가 많음 → **의미 판단은 LLM, 기계적 검사만 규칙.**

**① 팀원은 자유롭게 쓰고, 그 글이 그대로 원문이 된다. 서버 LLM이 그 글에서 주장을 뽑는다.**
```
팀원(또는 팀원의 AI)이 쓴 노트 ─▶ (D11 정규식) ─▶ 원문 저장(D3) ─▶ 서버 LLM이 주장 추출
                                                              (주제·값·조건·종류·인용·문장)
```
- 보내는 것: 글 + (선택) 문서 이름.
- 예: "v1 데이터에서 XGBoost AUC 0.842, LightGBM 0.835. 그래서 v1은 XGBoost로 간다." → 관측 `best_model=XGBoost (dataset=v1)` + 결정 `model_choice=XGBoost (dataset=v1)`.
- 입력 경로는 하나(구조화된 주장을 직접 보내는 길은 만들지 않음).

**② 역할 분담과 재시도**
| 종류 | 예 | 담당 |
|---|---|---|
| 기계적 검사 | 인용 글자 일치, 필수 칸, id 존재, 종류 값 | 규칙 |
| 의미 판단 | 주제가 같은가, "피처 12개" = `n_features: 12`, 관측/결정 | 서버 LLM |
- 규칙 검사에 걸리면 오류를 LLM에게 돌려주고 **최대 2번 재시도** (예: "인용이 원문에 없음. 가장 비슷한 구간: …").
- 그래도 실패하면 원문은 저장된 채로 두고 팀원에게 "주장을 뽑지 못했음" 알림.

**③ 주제 맞추기**
1. 규칙: 대소문자·띄어쓰기·`_`·`-`만 다르면 같은 주제.
2. 서버 LLM: 기존 주제 목록(주제마다 예시 주장 1~2개)을 보고 같은 주제를 고르거나 새 주제를 만듦. 언어가 다른 경우(`best_model`/"최고 모델")도 여기서 잡음.
3. 그래도 생긴 중복은 사람이 별칭으로 합침.
- 제외한 것: "같은 원문을 인용하면 중복 의심 제안" 단계.

**④ 조건 키·값 맞추기:** LLM이 기존 키에 맞춰 뽑음("피처 12개" → `n_features: 12`). 규칙은 숫자 문자 → 숫자, 대소문자 무시만.

**④-2 (D6에서 추가) 값도 기존 값 이름에 맞춤.** 예: `XGB` → `XGBoost`.

**⑤ 관측/결정 분류:** LLM. 결정 = 채택·기각·보류·"~를 쓴다/안 쓴다", 관측 = 측정·비교·관찰 결과. 한 문장에 둘 다 있으면 주장 두 개. **애매하면 관측**(결정은 다른 결정을 대체할 수 있어 잘못 분류 시 피해가 큼).

**⑥ 안전장치**
| 장치 | 내용 |
|---|---|
| 후보로 시작 | LLM이 뽑은 주장은 전부 후보 (D7) |
| 승인 화면 | 원문 글, 뽑힌 주장, 인용 위치를 나란히 |
| 정정 | 승인 뒤 발견하면 정정 주장 (D2 ⑤) |
| 출처 기록 | `written_by` = 서버 LLM 모델명 + 지시문 버전 |
| 재현 | 같은 글 + 같은 지시문 + 같은 모델이면 캐시 재사용 |

### D5. 조건 비교 — 확정

**다룬 문제:** H2, T4

**① 주장의 조건 키 하나는 세 상태 중 하나**
| 상태 | 뜻 | 예 |
|---|---|---|
| 값 | 이 조건에서의 결과 | `n_features: 12` |
| 전체 (`*`) | 원문에 "상관없다"는 근거가 있을 때만 | "피처 수와 상관없이 class_weight가 낫다" |
| 미기재 | 원문에 말이 없음 | 피처 수를 안 적은 메모 |

**② 주제별 관련 조건 키(자동 계산):** 그 주제의 주장들에 한 번이라도 쓰인 키.

**③ 질문 조건 대 주장 조건**
| 경우 | 처리 |
|---|---|
| 주장 값 = 질문 값 | 맞음 |
| 주장 값 ≠ 질문 값 | 안 맞음. 빼고, 가장 가까운 기록 3개만 "조건이 다름" 안내 |
| 주장이 전체(`*`) | 맞음 |
| 주장이 관련 키를 미기재 | **"조건 미확인"으로 포함하고 표시.** 답변 규칙: 그 사실을 밝힐 것 (D9에서 검사) |
| 질문이 관련 없는 키를 말함 | 무시 (Q08 원래 버전이 질문 수정 없이 처리됨 → H2 해결) |
| 질문이 관련 키를 말하지 않음 | 그 키의 모든 값 포함, **조건별로 묶어서** 반환. 묶음마다 상태 4가지 중 하나 |
- 기각한 대안: 미기재를 빼서 "근거 없음"으로 처리(조건 덜 적은 기록이 쓸모없어짐).

**④ 질문 해석은 서버 LLM이 하고, 해석 결과("이렇게 이해했음")를 응답에 보여줌.**

**⑤ 값 비교는 정리 후 정확히 같은지만.** 범위·부등식("피처 10개 이상")은 1차 범위 밖(문자 그대로 저장·비교).

### D6. 기록 사이의 관계 — 확정

**다룬 문제:** H3, T1, T5

**① 같은 주제, 같은 종류끼리만 비교.** 주제는 D4에서 LLM이 뜻으로 맞춤(T1 해결).

**② 관계는 구조화된 칸을 보고 규칙으로 판정 (위에서부터 순서대로)**
| 순서 | 확인 | 관계 | 효과 |
|---|---|---|---|
| 1 | 같은 원문 문서에서 인용 구간(start/end)이 겹침 (버전 무관) | 재인용 | 연결만, 독립 근거로 안 셈 (T5 해결) |
| 2 | 새 주장이 `corrects`로 옛 주장을 가리킴 | 정정 | 승인되면 옛 주장 "정정됨" |
| 3 | 관련 조건 키 중 값이 다른 것이 있음 | 조건 다름 | 둘 다 유지 |
| 4 | 한쪽이 관련 조건을 미기재 | 비교 필요 | 둘 다 보여주고 "조건 미확인" |
| 5 | 조건 같고 값 같고 근거 다름 | 지지 | 독립 근거 +1 |
| 6 | 조건 같고 값 다름 | 충돌 | ③ |
- 전체(`*`) 조건은 어느 값과도 같은 조건으로 봄.

**③ 충돌 처리는 종류별로**
| | 결정끼리 충돌 | 관측끼리 충돌 |
|---|---|---|
| 옛 주장 작성자가 승인 | **결정 변경.** 옛 결정 = 이전 결정(대체됨), 새 결정 = 현재 결정 | 둘 다 유지, "같은 조건에서 측정이 엇갈림" |
| 옛 주장 작성자가 거절 | 새 결정 거절, 옛 결정 유지 | 새 관측 거절 |
| 대기 중 | 둘 다 보여주고 "현재 결정 미정, 충돌" | 둘 다 보여주고 충돌 |
| 해소 방법 | 승인 | 정정 주장만 |
- **결정 변경을 따로 신고하는 절차는 없음.** 새 결정이 충돌로 잡히고 옛 결정 작성자가 승인하면 변경. 자기 결정은 본인 승인으로 변경.
- 대체·정정된 주장은 지우지 않음. 현재 질문에서 빠지고, 이력 질문에서는 "이전 결정" 표시로 나옴.

**우리 데이터 확인:** R02–R01 재인용, R03–R01 조건 다름, R04–R01 관측 충돌(Q02는 충돌 유지), R09·R10·R11 재인용(독립 근거 1).

### D7. 승인과 신원 — 확정 (B안)

**다룬 문제:** H4, T8

**① 필요한 승인 (결정권자 선택: B안 = 작성자 본인)**
| 상황 | 필요한 승인 |
|---|---|
| 모든 주장 | 작성자 본인 ("내 글에서 맞게 뽑혔다" 확인) |
| 충돌 (D6) | + 충돌한 옛 주장의 작성자 |
| 남의 주장을 정정 | + 그 주장의 작성자 |
| 조건 다름 / 지지 / 재인용 / 비교 필요 | 추가 없음, 관련 작성자에게 알림만 |
- 기각한 A안: 작성자 + 다른 팀원 1명 이상(두 사람 원칙).
- 그 결과 "승인"의 뜻 = **작성자가 확인했고 다른 팀원과 충돌하지 않음.** 막을 실패 2번 = 작성자가 확인 안 한 AI 추출 결과를 사실처럼 말하기.
- **답에는 승인한 사람 이름을 항상 표시** (예: "v1 결측치는 중앙값 대체 (승인: 박재원)").

**② 상태 (계산)**
| 상태 | 뜻 |
|---|---|
| 후보 | 필요한 승인이 아직 다 안 됨 |
| 승인 | 필요한 승인이 전부 됨 |
| 거절 | 필요한 승인자 중 한 명이라도 거절 |
| 이전 결정 / 정정됨 | D6에서 대체됨 |
- 거절된 주장은 답에서 빠지고 기록은 남음. 자동 승인 없음. 승인함에 대기 기간 표시.

**③ 투표 = 한 사람이 주장 하나에 "승인" 또는 "거절".**
- 바꿀 수 있음: 새 투표를 추가하고 시간상 마지막 것이 유효. 이력 남음.
- 투표에 당시 본 내용(주장 + 당시 관계)의 해시를 저장. 이후 관계가 바뀌면(예: 별칭 합치기) 그 투표는 "다시 확인 필요".

**④ 승인은 사람만, 전용 웹 화면에서.** MCP에는 승인 도구 없음(AI가 스스로 승인하는 실수 방지). 한계: 진짜 사람인지는 로그인이 있어야 보장되고, 로컬 배포(D12)에서는 팀 안의 신뢰가 전제.

**⑤ 신원:** 저장소에 팀원 명단(`members.json`). 모든 글·투표에 팀원 id.

**⑥ 승인함**
| 할 일 있음 | 알림만 |
|---|---|
| 내 글에서 뽑힌 주장 확인 | 내 주장과 조건이 다른 기록 |
| 내 주장과 충돌하는 새 주장 | 내 주장을 지지하는 기록 |
| 내 주장을 정정하는 새 주장 | |

### D8. 질문 처리 — 확정

**다룬 문제:** H7, T4

```
질문 ─▶ ① 해석(서버 LLM 1회) ─▶ ② 주제의 주장 전부 ─▶ ③ 거르기(규칙) ─▶ ④ 상태(규칙) ─▶ ⑤ 응답
```

**① 해석:** 기존 주제 목록(예시 포함)을 주고 주제(여러 개 가능), 조건, 질문 종류(현재/이력, **기본 현재**)를 뽑음. 맞는 주제가 없으면 바로 근거 없음.

**② 그 주제(별칭 포함)의 주장을 전부 모음.** BM25 상위 몇 개가 아님 → 후보에서 정답이 빠지는 문제(H7) 제거. 의미 판단을 입력 때(D4) 해두므로 질문 때 LLM은 해석 1번.
- **원문 텍스트는 넘기지 않음.** 주장으로 뽑히지 않은 원문은 인용 검사·조건 정리·승인을 거치지 않았기 때문.

**③ 거르기 (순서)**
| 순서 | 대상 | 처리 |
|---|---|---|
| 1 | 거절된 주장 | 뺌 |
| 2 | 대체·정정된 주장 | 현재 질문: 빼고 "이전 결정: …" 한 줄 안내 / 이력 질문: 포함, "이전 결정" 표시 |
| 3 | 조건 (D5) | 맞음 / 미확인(표시) / 안 맞음(빼고 가까운 3개 안내) / 질문에 조건 없음(조건별 묶음) |
| 4 | 원문 새 버전 (D3 ⑤) | 확인됨 / 사라짐 안내 |
| 5 | 민감 정보 | (D11: 저장 전에 이미 정규식 처리) |

**④ 상태 (기존 하네스 규칙)**
| 남은 주장 | 상태 |
|---|---|
| 없음 | 근거 없음 (+ 가까운 조건 안내) |
| 같은 조건에서 값 2개 이상 (승인·후보 섞여도) | 충돌. 주장마다 승인 여부·승인자 |
| 값 하나, 승인된 주장 있음 | 답할 수 있음. 승인자, 독립 근거 수(재인용 묶음) |
| 값 하나, 후보뿐 | 승인 전 |

**⑤ 응답 필드:** `ask_id`, `understood_as`, `status`(또는 조건별 묶음과 묶음별 상태), `evidence`(최대 10개, 재인용은 묶음, 각 근거에 번호 `ref`), `notes`, `answer_rules`(상태별 정해진 문장), `safe_answer`(D9).

**한계:** 주제 맞추기(D4)가 맞다는 전제. 틀린 주제·뽑히지 않은 정보는 못 찾음 → 별칭, 승인 화면으로 대비.

### D9. 답 단계 검사 — 확정 (A안)

**다룬 문제:** H6, T3

**전제:** 최종 답은 팀원의 AI가 쓰고 사용자에게 직접 보냄. 서버는 가로챌 수 없어 검사를 강제할 수 없음.

**① `ask` 응답에 추가:** 근거 번호 `[1]`, `[2]` / `safe_answer`(상태와 근거로 규칙이 만든 템플릿 답).

**② `check_answer(ask_id, answer)` 도구.** AI가 답을 사용자에게 보여주기 전에 호출하도록 서버 안내문과 `answer_rules`로 안내. 검사 없이 나간 질문 수를 서버가 기록.

**③ 검사 내용**
| 담당 | 검사 |
|---|---|
| 규칙 | 답에 쓴 근거 번호가 실제로 넘긴 번호인가 / 민감 정보 형식이 있는가 |
| 서버 LLM | 상태별 체크리스트 (아래) |

| 언제 | 확인 |
|---|---|
| 항상 | 근거에 없는 사실·숫자를 말하지 않았나 / 질문 조건과 다른 조건의 결과를 답으로 쓰지 않았나 |
| 충돌 | 양쪽을 다 제시했나 |
| 승인 전 | 팀 사실·확정이라고 말하지 않았나 |
| 근거 없음 | 값을 단정하지 않았나 |
| 조건 미확인 근거 사용 | 그 사실을 밝혔나 |
| 현재 질문 | 이전 결정을 현재처럼 말하지 않았나 |
- 숫자·값 이름 일치는 예외가 많아("v1"의 1, "XGB") 규칙이 아니라 LLM이 봄.

**④ 실패 시:** 문제 문장 + 고칠 방법을 돌려주고 AI가 고쳐 재검사(최대 2번). 그래도 실패하면 `safe_answer` 사용. 답을 통째로 버리지 않음(T3 대응).
```json
{"pass": false,
 "problems": [{"type": "후보를 사실처럼", "sentence": "v2에서는 SMOTE를 쓰기로 했습니다.",
               "fix": "근거 [1]은 승인 전 후보입니다. '아직 승인되지 않은 기록에 따르면'처럼 밝히세요."}]}
```
- 기각한 B안: 서버가 답까지 쓰고 AI는 전달만(전달하며 바꿀 수 있어 보장 안 됨, D1 변경 필요).
- 팀원 레포의 "답 = 원문 구간 그대로"는 쓰지 않음. 근거는 이미 글자 그대로 검증된 인용(D3)이고, 답은 근거 번호로 연결.

### D10. 새 기록이 과거 결정에 영향을 줄 때 알림 — 향후 과제

**미룬 이유:** 막을 실패 1~5번을 직접 막지 않음(실제로 바뀐 결정은 D6이 처리) / 팀원 CPython 실험에서 효과 미확인(1/5, 채택 보류) / 잘못된 알림이 쌓이면 승인함을 안 보게 됨 / 멘토 숙제(범위 축소)와 반대. 팀원의 주된 작업이므로 팀원과 논의 권장.

**설계 메모 (재개 시 출발점)**
- 대상: 새 관측과 승인된 현재 결정의 짝.
- 연결: D4 구조화 때 서버 LLM에게 현재 결정 목록도 보여주고 `may_affect: [결정 id], 이유`를 받음(추가 호출 없음). 규칙으로 결정 존재·승인·시간 순서·관측 여부·바뀐 조건을 확인.
- A~E 분류 없음. 결정자에게 "검토 요청 + 이유 + 바뀐 조건"만. 결정자가 무시 / 재비교 예정 / 결정 바꾸기(새 결정 → D6) 선택. 무시·재비교 예정은 투표 기록의 한 종류.
- 팀원의 가린 읽기/공개 읽기는 생략(새 증거가 새 관측 주장으로 명시적임).
- 열린 검토 요청은 그 결정에 대한 질문 답에 안내로 붙음(상태 불변).
- 평가 사례: 팀원의 CPython 3건, Aimers 사례.

### D12. 저장과 동기화 — 확정

**다룬 문제:** H5

**① 배포: 로컬 서버 + 공유 Git 레포 (A안).** 팀원마다 자기 PC에서 하네스(MCP 서버) 실행, 기록은 공유 GitHub 레포로 주고받음. **저장 부분은 인터페이스 뒤에 두어 나중에 중앙 서버 + DB(B안)로 바꿀 수 있게.**
- 받아들인 약점: 신원 확인이 약함, pull 전까지 남의 기록이 늦게 보임.

**② Git 작업은 하네스가 자동으로**
| 시점 | 동작 |
|---|---|
| 질문·글 올리기 직전 | `git pull` |
| 글 올리기·투표 직후 | 새 파일 커밋 + `git push` |
| push 거부 | 다시 pull 후 재시도 (모든 기록이 이름이 겹치지 않는 새 파일이라 충돌 없음) |
| 오프라인 | 로컬에 쌓았다가 연결되면 push |

**③ 앞뒤 순서는 시계가 아니라 "올릴 때 본 기록"(`seen`).** 주장을 올릴 때 그 순간 내 저장소에 있던 같은 주제 주장 id들을 기록. B의 `seen`에 A가 있으면 A가 먼저. 서로 못 본 채 올린 동시 제출이 충돌이면 **양쪽 작성자가 서로 승인.** (팀원 레포 `parents` 방식)

**④ 저장소 구조**
```
team-records/            ← 공유 GitHub 레포
├── members.json
├── sources/<해시>.json
├── claims/<해시>.json
├── votes/<해시>.json
└── aliases/<해시>.json

각자 PC의 .cache/ (Git에 안 올림): 계산된 상태·관계, LLM 응답 캐시
```

**⑤ (D14로 대체됨)** 원래 "LLM 키는 팀원 각자"였으나, 서버 LLM이 학교 GPU 서버 한 곳으로 정해져 필요 없어짐.

### D13. MCP 인터페이스 — 확정

**① 도구 4개 (승인 도구 없음)**
| 도구 | 입력 | 하는 일 | 성격 |
|---|---|---|---|
| `submit_note` | 글, (선택) 문서 이름 | 정규식 → 원문 저장 → 서버 LLM 주장 추출 → 인용 검사·재시도 → 관계 계산 → Git push | 쓰기 |
| `ask` | 질문 문장 하나 | D8 전체. 근거 번호, `safe_answer`, 답변 규칙 반환 | 읽기 |
| `check_answer` | `ask_id`, 답 | D9 검사 | 읽기 |
| `my_inbox` | 없음 | 승인할 것·알림 요약 + 승인 화면 주소 | 읽기 |
- 같은 문서 이름으로 다른 내용을 올리면 새 버전(D3).
- 보통 길이의 글은 끝날 때까지 기다렸다 결과 반환, 긴 문서는 "처리 중" 반환 후 뒤에서 처리(결과는 `my_inbox`).

`submit_note` 응답 예
```json
{"source": "note_031@1",
 "masked": "전화번호 1개를 가렸습니다",
 "claims": [{"id": "clm_9b1…", "kind": "decision", "topic": "missing_value", "value": "KNN",
             "conditions": {"dataset": "v1"}, "quote": "v1 결측치는 KNN 대체로 바꾼다", "status": "후보"}],
 "relations": ["R12(박재원, 중앙값 결정)와 충돌 → 박재원의 승인도 필요"],
 "next": "승인 화면에서 확인해 주세요: http://localhost:8765/inbox"}
```

**② 리소스 2개:** `harness://claims/{id}`(주장 상세), `harness://policy`(상태 뜻과 답변 규칙). **원문은 MCP로 노출하지 않음**(D8 원칙). 원문은 승인 화면에서 사람만.

**③ 프롬프트 2개:** "팀 기록으로 올리기", "팀 기록으로 질문하기".

**④ 서버 안내문(연결 시 AI에게 전달)**
- 팀의 결정·실험 결과 질문에는 먼저 `ask`.
- 답을 보여주기 전에 `check_answer`. 실패하면 고쳐서 재검사, 계속 실패하면 `safe_answer`.
- 답에는 근거 번호 `[n]`.
- 승인 전 후보를 팀 사실이라고 말하지 않음.
- 승인은 사람이 화면에서 함. AI는 승인하지 않음.

**⑤ 실행 명령:** `harness mcp`(클라이언트가 stdio로 실행), `harness review`(승인 화면 로컬 웹페이지). 둘은 같은 저장소 폴더 사용.

**실행 시나리오 요약 (설계 검증용)**
1. 박재원: "v1에서 중앙값이 KNN보다 AUC 0.003 높아서 중앙값으로 가기로" → `submit_note` → 관측 1 + 결정 1 후보 → 승인 화면에서 본인 승인.
2. 정시찬: "v1 결측치 처리 어떻게 하기로 했어?" → `ask`(answered, 근거 [1], 승인: 박재원) → 초안 → `check_answer` 통과 → 답.
3. 정시찬: "KNN k=5가 0.006 더 높아, KNN으로 바꾸자" → 결정 충돌, 박재원 승인 필요 / 관측은 비교 필요(k 조건 미기재).
4. 승인 전 질문 → 충돌. 초안 "이제 KNN으로 처리합니다"는 `check_answer`에서 실패 → 두 결정을 모두 제시하는 답으로 수정.
5. 박재원: `my_inbox` → 승인 화면에서 승인 → KNN 현재 결정, 중앙값 이전 결정.
6. 이후 질문: "KNN [1] (승인: 정시찬, 박재원). 이전에는 중앙값." / "예전엔?" → 이력 질문.

Claude Desktop 설정 예(구현 후)
```json
{"mcpServers": {"knowledge-harness": {
   "command": "harness",
   "args": ["mcp", "--store", "C:/team-records", "--member", "정시찬"]}}}
```

### D14. LLM — 확정

**① 학교 GPU 서버(RTX 3090, 24GB) + vLLM.** 팀 전원이 이 서버 하나를 씀(D12 수정: 모델은 각자 PC가 아님). 팀 전원이 자동으로 같은 모델을 쓰게 됨.
- 장시간 운용 가능(한 번에 최대 약 4일). **재시작은 필요할 때 직접.** 재시작 스크립트는 만들지 않음.
- 접속 주소는 설정 한 곳에서 관리(재배정 시 노드가 바뀔 수 있음). 가능하면 SSH 터널로 고정 주소.
- vLLM은 OpenAI 방식 주소와 JSON 형식 강제(guided decoding)를 지원 → `llm.py`는 접속 주소만 바꾸면 됨.

**② 모델: Qwen 8B급 BF16(양자화 없이)으로 시작.** 부족하면 14B 4비트(AWQ) → 32B 4비트(입력 한도 축소 필요) 순서.

**③ 결과가 매번 같게:** temperature 0, JSON 스키마 강제, 추론 모드(thinking) 기본 끔, 지시문 버전 기록.

**④ 입력 길이:** 입력 한도를 명시적으로 지정. 주제가 100개를 넘으면 노트와 단어가 많이 겹치는 상위 30개만 보여줌. 긴 문서는 몇천 자 단위로 나눠 처리.

**⑤ 모델 서버가 꺼져 있을 때**
| 도구 | 처리 |
|---|---|
| `submit_note` | 원문은 저장, "주장을 뽑지 못함" 알림. 서버가 켜지면 밀린 구조화 처리 |
| `ask` | "지금 답할 수 없음, 모델 서버 확인 필요". 추측 답 안 함 |
| `check_answer` | "검사 불가" → AI는 `safe_answer` |

**⑥ 모델은 채택 전 품질 확인(D15 1층)을 통과해야 쓴다.** 기준은 측정 전에 고정.

**⑦ GPT 계열과의 비교는 하지 않음** (결정권자 결정, 필요해지면 나중에).

### D15. 평가 — 1층 우선, 2·3층 나중

**3층 구조 (구조 자체는 논의함, 1층만 우선 진행)**
| 층 | 묻는 질문 | 상태 |
|---|---|---|
| **1층: 부품 정확도 = 채택 전 품질 확인** | 각 부품이 자기 일을 정확히 하나 | **지금 진행** |
| 2층: 효과 분리(ablation) | 각 장치가 최종 결과(실패 1~5번)에 기여하나 | 나중 |
| 3층: 전체 비교 | 하네스가 다른 방식보다 나은가 | 나중 |

"채택 전 품질 확인"과 "모듈별 실험(효과 분리)"의 차이: 전자는 부품을 따로 시험대에 올려 정확도를 재는 것(관문), 후자는 부품을 뺀 시스템으로 최종 결과의 차이를 보는 것. 결정권자가 원한 것은 전자(1층).

**1층 LLM 부품 시험 (기준 제안값: 측정 전에 고정)**
| 부품 | 맞혀야 하는 것 | 기준 |
|---|---|---|
| 주장 뽑기 (D4) | 주제·값·조건 | 90% |
| 관측/결정 분류 (D4) | 종류 | 90% |
| 인용 (D3·D4) | 재시도 후 원문 일치 | 95% |
| 질문 해석 (D8) | 주제·조건·현재/이력 | 90% |
| 답 검사 (D9) | 나쁜 답 잡기 / 좋은 답 통과 | 90% / 90% |
- 기준 미달 시 순서: 추론 모드 켜기 → 더 큰 모델 → 지시문 개선 → 재시험.

**1층 규칙 부품 테스트 (정답이 정해진 테스트, 100% 통과)**
| 부품 | 테스트 |
|---|---|
| 인용 검증 (D3) | 정상 통과 / 숫자 바꾼 인용 거부 / 부정문 뒤집은 인용 거부 / 공백만 다른 인용 통과 / 300자 이하 자동 인용 |
| 조건 비교 (D5) | D5 ③ 표의 6가지 경우 |
| 관계 판정 (D6) | 재인용, 정정, 조건 다름, 비교 필요, 지지, 충돌(관측·결정) |
| 상태 결정 (D8) | 상태 4가지 + 조건별 묶음 |
| 앞뒤 순서 (D12) | 먼저 본 기록 / 동시 제출 |

**시험 데이터:** 결정권자가 **학교 NAS에 새 시험 데이터셋을 저장해 둠.** 형식은 아직 공유되지 않음(7절의 확인 사항).

**제안 (미확정) — 1층 데이터와 절차**
- 개발용 40% / 시험용 60% 분리. 지시문·모델 조정은 개발용 결과만 보고, 시험용은 마지막에 한 번.
- 정답은 두 사람이 따로 표시 후 일치율 기록, 다른 부분만 합의(T7 대응).
- 사전 고정: 정답, 기준 숫자, 지표 정의, 지시문 버전을 시험용 실행 전에 해시로 고정(팀원 레포 `freeze.json` 방식).
- 모든 LLM 호출의 입력 해시와 출력을 저장해 서버 없이 재채점 가능하게.
- 통계: 정확도 + 부트스트랩 95% 신뢰구간.

**제안 (나중에 논의) — 2·3층**
- 2층: 조건 비교, 승인 구분, 재인용 묶기, 입구 인용 검증, 대체·정정, 답 검사를 하나씩 끄고 실패 1~5번 지표 비교. **호출 횟수를 맞춘 비교군**(답 검사 대신 AI가 체크리스트 없이 자기 답을 한 번 더 검토) 포함.
- 3층: BM25 / 전체 맥락 LLM / Graphiti / 하네스. 공통 답변기 = 같은 Qwen. Graphiti도 같은 Qwen으로(작은 모델에서 형식 처리 실패 가능 → 개발용으로 먼저 확인). GroupMemBench는 2차 범위라 재실행 안 하고 기존 결과를 참고로. 여러 사람 시나리오(13절 시나리오) 스크립트 테스트.

## 7. 지금 할 일: 1층 평가 착수

### 7.1 진행 방식
- 이 대화(클라우드 세션)는 학교 NAS·GPU에 접근할 수 없었음.
- **방법 2로 결정:** 결정권자 PC(`LAPTOP-D4EC1COR`, 폴더 `D:\26-2\캡디\knowledge_harness\knowledge_harness`)에서 새 Claude Code 세션을 열고, 그 세션이 SSH로 학교 서버에 접속해 작업한다. 새 세션은 이 문서를 읽고 이어간다.

### 7.2 새 세션이 먼저 확인할 것 (결정권자에게 물을 것)
1. **NAS 시험 데이터셋 형식:** 폴더 구조, 파일 형식, 파일마다 샘플 2~3개.
2. **정답 표시 범위**
   - 노트: 정답 주장의 주제·값·조건·종류(관측/결정)·인용이 있나
   - 질문: 정답 주제·조건·현재/이력·기대 상태가 있나
   - 답: 좋은 답/나쁜 답 구분과 실패 유형이 있나
3. **개발용/시험용 분리 여부** (없으면 D15 제안대로 40/60을 결정권자에게 확인 후 적용)
4. **정답을 누가 표시했나** (두 사람 독립인지)
5. **주제 이름 채점 방식 결정**
   - (a) 개발용 데이터의 주제·조건 키·값 목록을 "이미 있는 목록"으로 넣고, 모델이 그 목록에서 맞게 고르는지 봄(D4 실제 동작과 같음)
   - (b) 이름은 무시하고 같은 주제여야 할 주장들을 같은 주제로 묶었는지(묶음 일치) 봄
6. **학교 서버 정보:** SSH 접속 주소, vLLM에 띄울 정확한 모델 이름, 데이터 경로. 경희대 Seraph 클러스터(Slurm)일 가능성 있음(확인 필요).
7. **1층 기준 숫자(90/95%) 확정** 후 측정 전에 고정.

### 7.3 구현 순서 (제안)
1. `harness_v2/llm.py`: vLLM(OpenAI 호환) 연결. `base_url`·모델명 환경변수, temperature 0, JSON 스키마 강제(`response_format` json_schema, 안 되면 `extra_body.guided_json`), Qwen 추론 모드 끄기(`extra_body.chat_template_kwargs.enable_thinking=false`), 디스크 캐시, 호출 기록(JSONL: 입력 해시·출력·모델·지시문 버전).
2. `harness_v2/quote.py`: D3 인용 검증(공백 정규화 후 정확 일치, 위치 찾기, 가장 비슷한 구간, 300자 이하 자동 인용) + 테스트(부정문 뒤집기 포함).
3. `harness_v2/structure.py`: D4 주장 추출(기존 목록 입력, 재시도 2번, 정규화).
4. `harness_v2/interpret.py`: D8 질문 해석.
5. `harness_v2/check.py`: D9 답 검사(규칙 + 체크리스트).
6. `eval/layer1.py`: 데이터 로더(NAS 형식에 맞춤), 개발/시험 분리, 사전 고정(해시), 부품별 지표 + 부트스트랩 신뢰구간, 기준 통과 여부 표.
7. 규칙 부품 테스트(D5·D6·D8 상태·D12 순서)는 해당 부품을 구현하면서 추가.
